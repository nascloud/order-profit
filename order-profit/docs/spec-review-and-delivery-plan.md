# 《订单利润核算标准化程序开发文档》审查与实施计划

- **审查日期**：2026-08-10
- **审查对象**：仓库根目录《订单利润核算标准化程序开发文档》
- **结论**：**有条件可开发**。输入读取、审计骨架和多数清洗规则可以启动；利润公式、回归基准、运费兜底、售后复核、正式交付状态及用户界面范围必须先完成业务决策。
- **原文状态**：本报告不修改原始开发文档。

## 1. 执行摘要

当前文档已经具备较好的业务边界、异常意识和勾稽框架，但尚不能直接作为无歧义的开发合同。主要原因是：

1. “订单利润”的定义包含平台扣点和综合税赋，但所有计算公式、输出字段和回归基准均未包含。
2. 运费虽然规定了实际运单的共享冲突，却没有定义成本编码表中“标准运费”的金额粒度，可能在多明细订单中重复扣费。
3. 售后表只说“复核”，但没有可执行的匹配、汇总、期间与差异判断算法。
4. 缺成本/运费时允许继续输出部分利润，但没有定义是否可以标记为“正式交付”。
5. “友好的用户界面”与只定义 CLI、首版不建设 Web 的范围不一致。
6. Excel 强制重算被列为交付前置条件，但运行环境并不保证存在 Excel 或 LibreOffice，也未说明哪些单元格必须使用公式。

## 2. 阻断级业务决策

### D-01 平台扣点与综合税赋

**引用**：第 46 行、第 263–268 行、第 345–357 行、第 513–520 行。

**冲突证据**：

```text
47,621.07 - 226.58 - 28,039.45 - 4,908.92 = 14,446.12
14,446.12 - 1,178.39 - 7,942.86 = 5,324.87
```

回归基准完全采用“不扣平台扣点、不扣综合税赋”的公式，与第 46 行的利润定义冲突。

**必须选择**：

- **方案 A（推荐）**：正式纳入平台扣点和税赋；补充平台识别来源、计费基数、退款影响、逐行舍入规则，并重建第 13.3 节全部基准值。
- **方案 B**：首版明确不纳入，删除第 46 行对应内容，并将其列为 V2 非目标。

若采用方案 A，还必须明确：

- 平台类型是整次运行配置、店铺配置，还是订单逐行字段；混合平台如何处理。
- 平台扣点基数是实收金额、实收减退款，还是平台账单口径。
- 综合税赋基数是否扣除退款、平台费或其他费用。
- 退款发生在跨期时是否回溯原订单期间。
- 平台费与税赋是否逐明细 `ROUND_HALF_UP` 到分后再汇总。

### D-02 成本表“标准运费”的粒度

**引用**：第 87、249–257 行。

必须明确标准运费表示：

- 每订单明细总运费；
- 每件运费，需要乘购买数量；
- 每主订单运费，需要主订单内分摊；
- 每包裹运费，需要包裹关系。

**推荐首版**：定义为“订单明细总运费候选值”，不乘数量；但同一主订单存在多条有效明细且均无可用实际运费时，禁止对每行直接重复套用同一个订单级运费。若业务不能证明其为明细级运费，应保持未核算。

### D-03 售后复核算法

**引用**：第 101–111、476 行。

必须明确：

- 售后表 `订单编号` 对应订单表的 `主订单编号` 还是其他编号。
- 一个主订单多条订单明细、多笔退款时如何汇总。
- 哪些售后状态属于最终成功。
- 售后复核按订单付款期间还是退款完结期间过滤。
- 同一退款编号内容冲突时是失败还是保留异常。
- 金额差异是按主订单合计比较，还是必须定位到明细。

**推荐首版**：售后表按退款编号去完全重复；冲突记录阻止运行；成功退款按主订单编号汇总，仅与订单表同主订单的有效退款合计比较，不回填利润。无法唯一落到订单明细时只报告主订单级差异。

### D-04 缺成本/运费时的交付状态

**引用**：第 270–276、289、470–479 行。

文档允许继续运行并生成“部分已核算利润”，但又要求正式交付勾稽通过。金额内部勾稽通过并不代表利润完整。

**推荐状态模型**：

- `FAILED`：输入、唯一性、公式或勾稽失败；不生成正式报告。
- `PROVISIONAL`：核算逻辑通过，但存在有效正常/关闭订单成本或运费缺失；报告加醒目标记，不得称为最终净利润。
- `FINAL`：核算完整，所有强制校验通过。

CLI 对 `PROVISIONAL` 默认返回 0 但打印警告，另提供 `--require-complete` 使其返回非零，便于正式流水线验收。

### D-05 用户界面范围

**引用**：第 23、151–168、400–411、434 行。

“友好的用户界面”没有验收定义；当前只有 CLI 和输出 HTML，且 HTML 是分析页，不是输入操作界面。

**推荐首版范围**：

1. P0：CLI 完成全部能力，并提供中文错误、进度日志和运行摘要。
2. P1：使用 Python 标准库 Tkinter 提供本地桌面启动器，只负责选文件、日期、输出目录、策略选项与显示运行结果；不复制业务逻辑。
3. HTML 保持只读分析报告，不建设 Web 后端。

若业务认为 CLI + 报告 HTML 已足够，则应删除“用户界面”验收措辞。

### D-06 Excel 公式与重算责任

**引用**：第 128、373–375、434、467、536 行。

openpyxl 不计算公式；Windows Excel COM 仅在安装了桌面 Excel 时可用，LibreOffice 的兼容性也不能默认保证。文档还没有指定哪些报表值必须写公式。

**推荐方案**：Python 内存结果是唯一核算事实来源，Excel 默认写入已计算值；只为辅助复核写少量公式。交付校验分两层：

- 必须：Python 勾稽、工作簿结构、公式字符串静态检查、写后读回值检查。
- 条件必须：若模板或配置启用了 Excel 公式，则要求 Excel COM 或 LibreOffice 重算，并校验缓存值；否则不把重算引擎作为基础运行前提。

若业务坚持所有汇总均由 Excel 公式计算，则必须把“安装 Microsoft Excel 的 Windows 主机”写入部署契约。

## 4. 建议的数据与计算架构

### 4.1 分层

```text
CLI / Tkinter 启动器
        ↓
Application Pipeline（流程编排、退出状态、运行清单）
        ↓
Domain Rules（清洗、分类、成本、运费、退款、利润、汇总、勾稽）
        ↓
Adapters（Excel/CSV 输入、Excel/HTML 输出、重算器）
```

GUI、CLI、Excel 和 HTML 都不得复制利润公式。所有业务计算只存在于 Domain Rules。

### 4.2 权威中间模型

每个源订单行在读取后获得不可变审计标识：

```text
source_file_id       输入文件 SHA-256 的短标识
source_sheet         原工作表
source_row_number    Excel 实际行号
source_row_id        file_id + sheet + row_number
```

订单流水线至少保留：

- 原始值列（必要审计字段）；
- 标准化 ID、日期、数量和金额；
- `cleaning_reasons[]`；
- 互斥 `partition`；
- 成本/运费最终值、来源、匹配键和未核算原因；
- 退款、平台费、税赋、利润及逐项状态；
- `calculation_status` 和 `issue_codes[]`。

### 4.3 金额模型

推荐内部权威金额全部使用整数“分”：

```text
输入文本/Excel值
  → Decimal(str(value))
  → ROUND_HALF_UP 到 0.01 元
  → 转为 int cents
  → 全部加减与勾稽使用整数
  → 输出时除以 100 显示
```

这样避免 pandas 浮点求和及 Excel 二进制序列化差异。百分比只在显示层计算；分母为零时同时输出值 0 和状态 `ZERO_DENOMINATOR`。

### 4.4 互斥分区

为了保证源订单行数守恒，每行最终只能属于一个一级分区：

1. `DELETED_BY_RULE`
2. `OUT_OF_PERIOD`
3. `NORMAL_CODED`
4. `CLOSED_SHIPPED_CODED`
5. `MISSING_MERCHANT_CODE`
6. `OTHER_STATUS`

输入无法标准化且规则要求阻止运行的行不进入正式分区统计，而进入失败运行的结构化错误清单。只有成功运行才执行第 9 项行数守恒勾稽。

### 4.5 策略配置

增加可序列化 `RunConfig`，并把完整快照写入 Excel“规则说明”、HTML 和 `manifest.json`：

- 日期范围、时区、工作表名；
- 平台费/税赋策略；
- 补充覆盖开关；
- D/S 大小写策略；
- 标准运费粒度；
- 推广完全重复策略；
- 是否要求核算完整；
- Excel 重算模式；
- schema/version 与程序版本。

### 4.6 输出事务

1. 读取所有输入并计算 SHA-256。
2. 在输出目录旁建立临时运行目录。
3. 完成计算、勾稽、Excel/HTML 写入和读回检查。
4. 生成 `manifest.json`、`issues.xlsx` 或异常工作表、运行日志。
5. 全部通过后原子移动为正式输出；失败时保留带 `FAILED` 标识的诊断目录，不覆盖上一份成功结果。

## 5. 建议补充的勾稽与质量闸门

除原 11 项外，增加：

1. 所有一级订单分区互斥，且成功运行时行数守恒。
2. 每一条已核算正常订单利润等于各组成项逐分相减。
3. 若启用平台费/税赋，链接与汇总对应费用逐分相等。
4. 已核算行数 + 未核算行数 = 有编码有效订单行数。
5. 每个可用实际运单最多被计入一条明细。
6. 每个生效补充记录恰好匹配一个源订单行；每个未生效补充有原因。
7. 推广商品汇总、每日汇总与推广明细的展现、点击、花费、成交均一致，而不只核对花费。
8. HTML 中的关键汇总值与内存结果、Excel 值逐分一致。
9. 输出不包含未转义业务文本形成的可执行 HTML。
10. `FINAL` 状态下成本/运费缺失行数必须为 0。

## 6. 测试方案补全

### 6.1 单元测试

在原 12 项基础上增加：

- D/S 大小写和 Unicode 文本边界；备注空值。
- 空付款时间、非法日期、带时区时间、结束日微秒边界。
- Excel 数字 ID、字符串 `.0`、前导零、超 15 位精度风险。
- 金额 `1.005` 的 ROUND_HALF_UP、负值、空白、科学计数法。
- 数量 0、负数、小数和超大值。
- 冲突成本编码、完全重复编码、空编码。
- 一个运单一行、多行共享、运费表冲突、人工补充覆盖共享运单。
- 补充状态、部分字段更新、覆盖开关、零值补充、重复键和多目标匹配。
- 正常订单完整/缺成本/缺运费；关闭订单完整/缺失。
- 平台费和税赋每一种平台与退款场景（若启用）。
- 推广零分母、完全重复、空 ID、日期边界。
- 商品标题确定性、仅推广链接利润、无效订单链接排除。
- HTML 转义与公式注入防护（以 `=`, `+`, `-`, `@` 开头的文本）。

### 6.2 性质与不变量测试

- 任意顺序重排输入行，汇总金额保持不变。
- 重复运行相同输入和配置，业务结果与 manifest 数据摘要一致。
- 给推广表增加合法末行，汇总严格增加对应值。
- 缺成本永远不能变成 0 或产生利润。
- 同一实际运费永远不会被计入两次。
- 链接集合严格等于有效订单商品 ID 与期间推广主体 ID 的并集。

### 6.3 集成样本矩阵

至少建立以下可提交的脱敏小样本：

- `happy_path`：正常、退款、关闭、仅推广、仅订单。
- `missing_cost_freight`：产生 `PROVISIONAL`。
- `shared_waybill`：共享实际运单阻断回退。
- `supplement_overwrite`：覆盖开/关各一组。
- `invalid_inputs`：每种阻断错误各一份最小样本。
- `rounding_edges`：分币舍入和百分比零分母。
- `formula_recalc`：仅在启用 Excel 公式时运行。

当前真实业务样本只作为私有回归 fixture，不能替代脱敏测试，也不应提交 Git。
